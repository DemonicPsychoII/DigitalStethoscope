# System requirements

Each requirement states an outcome that is testable on the finished device with this equipment:
headphones, phone, laptop, the HAPI web page, a pulse oximeter or smartwatch and test-tone audio.
The design defines how the device achieves these outcomes and sets the internal parameters. Flows
are shown in the [use-case diagrams](use-cases.md).

Registration and certificate tests belong to FHIR acceptance; they are not prerequisites for Wi-Fi setup.

Methods: **T** test (measured), **D** demonstration (shown working).

| ID | Requirement | How it is tested | Method | Pass |
|---|---|---|---|---|
| <a id="req-01"></a>REQ-01 | After power-on the device stays silent until Start is pressed. | Power on with volume at maximum and headphones on. | D | Silence until Start. |
| <a id="req-02"></a>REQ-02 | After Start the operator hears heart sounds. | Chestpiece on own chest, Raw filter, press Start. | D | Heartbeat audible within 2 s of Start. |
| <a id="req-03"></a>REQ-03 | The 3-position switch selects the Raw, Murmur or BPM listening filter. | Play 100 Hz, 400 Hz and 2 kHz tones from a laptop through an earbud held on the chestpiece diaphragm, at one fixed laptop volume and device volume for all positions. First confirm each tone is clearly audible in Raw; Raw is the reference. | D | Compared with Raw: Murmur keeps 100 Hz and 400 Hz, 2 kHz clearly quieter. BPM keeps 100 Hz and makes 400 Hz and 2 kHz clearly quieter. |
| <a id="req-04"></a>REQ-04 | The potentiometer sets the volume from silent to maximum. | Turn through the full range while listening. | D | Silent at minimum; loudest output at the maximum endpoint; no crackling throughout the sweep. |
| <a id="req-05"></a>REQ-05 | Listening has no noticeable delay. | Tap the chestpiece and listen. | D | Tap heard together with the touch; no echo or lag noticeable. |
| <a id="req-06"></a>REQ-06 | A heart session of at least 15 s gives a heart rate. | 10 sessions of 30 s and 3 sessions stopped at the 15 s boundary on own chest, pulse oximeter or smartwatch at the same time; use signals meeting the validity criteria. | T | Each result within ±5 BPM or ±10 % of the reference. |
| <a id="req-07"></a>REQ-07 | Stopping before 15 s gives no result. | Stop after 10 s and again at 14.9 s; record timing uncertainty and ensure the upper bound remains below 15 s. | T | Nothing sent to the server; nothing in the serial log as a result. |
| <a id="req-08"></a>REQ-08 | A poor signal gives an error instead of a number. | Two 30 s sessions: chestpiece held in open air for the whole session; diaphragm rubbed continuously against clothing for the whole session. | T | In both sessions: error on the server and on the device (LED and serial log); no BPM value. |
| <a id="req-09"></a>REQ-09 | With the configured server available, a valid result reaches the FHIR server linked to this device; unavailable or failed delivery follows REQ-10. The device never selects or adds a patient ID. It reuses a patient reference only when supplied with a server-requested examination; otherwise it sends no patient reference. | Run a synthetic server-requested examination with a supplied patient reference, then one without a reference; inspect outgoing requests and stored Observations. | T | Both Observations reference this device's Device, with a value meeting REQ-06 and the measurement-end timestamp, within 10 s of Stop; only the examination with a supplied patient reference includes that same reference in subject. |
| <a id="req-10"></a>REQ-10 | A failed delivery is retried up to 3 times within the overall deadline, then the device shows an error. Terminal failure discards the result; it is not retained for later delivery. | Stop the HAPI container before or during sending; repeat with the server restarted during the retries; then commit the first write, drop its receipt and let the device retry. After a terminal error, restore the server and inspect requests/HAPI until the next deliberately started measurement to check that the failed result is not resent. | T | At most 4 attempts within 10 s; error shown if all fail, with no later retry of that measurement after server recovery; in the committed-write/lost-receipt case exactly one Observation exists and every attempt uses the same conditional-create identity. |
| <a id="req-11"></a>REQ-11 | Selected open networks need no password; protected networks require valid credentials. Secure server transport checks the server certificate. | Test an open network, wrong/correct protected-network password, then certificates with an untrusted issuer, wrong server name and expired validity in separate FHIR-phase runs. | T | Open/correct joins work; wrong credentials fail; invalid server certificate prevents sending. |
| <a id="req-12"></a>REQ-12 | Without credentials or after a 2 s hold in Idle, the device provides an open hotspot portal to select Wi-Fi. Saved credentials survive restart. | Join hotspot without a password; use QR portal URL; select open/protected networks; verify address before saving, restart and rejoin; inject save failure. | T | Selected network joins; saved credentials persist; failed saving shows an error while retaining the connection and old valid settings. |
| <a id="req-13"></a>REQ-13 | Faults follow the feedback catalogue; Wi-Fi-only faults preserve working audio. Audio faults mute at once and block every input until restart. Other restart-required faults block Start until restart; when one occurs while listening, it takes effect only when the operator stops the examination. | Inject a Wi-Fi-only fault during listening, then Stop and press Start while offline; separately inject a microphone fault, press Start before restart, test short press, a 2 s hold, the switch and the volume, then restart after restoring the microphone; separately change the measurement context during listening, then Stop and press Start. | T | Wi-Fi fault does not interrupt audio and offline Start works after Stop; microphone fault mutes and shows its code at once, no input has an effect before restart, restart/checks restore operation; the context change does not interrupt listening or show an error, and after Stop no result is sent, the error is shown and Start is blocked until restart. |
| <a id="req-14"></a>REQ-14 | Errors show the catalogue context colour and counted red code; short-press-clearable errors can be acknowledged without implicit Start/retry. | Inject Wi-Fi join, credential-save and delivery failures; compare code/context, acknowledge with a short press and separately request Start or setup (VT-09). | T | Correct code and serial cause; acknowledgement follows catalogue; no implicit Start or manual retry. |
| <a id="req-15"></a>REQ-15 | The device keeps its server registration across restarts. | Record the server ID returned by first registration and its persisted value; restart three times, inspect reuse of that same ID and run a session after each restart (VT-15). | T | One Device for this device on the HAPI page; all Observations reference it. |
